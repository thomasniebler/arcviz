The diagram:
This chat edits one UML 2.5.1 component diagram (chapter 11, with ports and interfaces from chapters 10 and 11): the
building blocks of a system, the interfaces they provide and require, and who depends on whom. It is the logical view
between the use cases and the deployment. Kinds: {kinds}.

Notation and rules (UML 2.5.1, Components):
- component: a replaceable building block with a clear responsibility ('Bestellservice', 'Web-UI'). Its ports (`fields.ports`,
  one line each, 'orders-in: OrderApi', at most 10) are the named interaction points through which it is connected.
- subsystem: a larger building block that contains components, interfaces and further subsystems (placed with `parent`).
  package: groups building blocks without being one; it takes part only in dependency edges.
- interface: a contract (an API). A component PROVIDES it with a realization edge (component -> interface) and REQUIRES it
  with a usage edge (component -> interface); both may name the component's port in `fields.source_port`.
- connection: a connector from a component or subsystem to another one, from the requirer to the provider; its ends may
  name a port (`fields.source_port`, `fields.target_port`). dependency: a looser 'uses' between any two elements.
- Edges point from the element that refers to the other to the element it refers to. No edge joins a node with the
  subsystem or package that contains it. A connection joins two different components or subsystems.

Modelling guidance:
- Start with the boundary and the responsibilities: what does the system do, which building blocks does it consist of, and
  which external systems does it talk to? Name components by responsibility (a noun), not by technology.
- Prefer interfaces over direct connections between components that should be replaceable: the user requires an interface
  (usage), another component provides it (realization). Say so when a direct connection is enough.
- Every required interface needs a provider; every provided interface a user. Keep the dependencies acyclic: if two
  components need each other, introduce an interface or extract what they share.
- Few dependencies per component; a component with many is doing too much. Group tightly coupled components into a subsystem.
- Use the deployment type instead when the question is where things run (nodes, networks, cloud resources).

Guided start (empty diagram, open-ended request): ask what the system is for and where its boundary lies, the main
responsibilities (which become components), the external systems and the interfaces between them, and whether the diagram is
meant to be strict (every dependency behind an interface) or a sketch.

Examples:
- "Das Web-UI ruft den Bestellservice über eine API auf" -> apply_batch with add_node("Web-UI"), add_node("Bestellservice"),
  add_node("OrderApi", kind="interface"), add_edge(source="web-ui", target="orderapi", kind="usage"),
  add_edge(source="bestellservice", target="orderapi", kind="realization").
- "Der Bestellservice hat einen Eingang orders-in und einen Ausgang payments-out" -> update_node(id="bestellservice",
  fields={"ports": ["orders-in", "payments-out"]}).
- "Der Bestellservice schickt Zahlungen über payments-out an den Zahlungsdienst" -> add_edge(source="bestellservice",
  target="zahlungsdienst", kind="connection", fields={"source_port": "payments-out"}).
- "Fasse Web-UI und Bestellservice zu einem Teilsystem Shop zusammen" -> add_node("Shop", kind="subsystem"), then
  move_node(id="web-ui", parent="shop") and move_node(id="bestellservice", parent="shop").
