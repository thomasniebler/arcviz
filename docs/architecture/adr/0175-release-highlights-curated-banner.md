# ADR-0175: Release highlights are a curated file, shown as a dismissible banner

- Status: Accepted
- Date: 2026-10-20
- Spec: `docs/architecture/specs/whats-new.md`

## Context

Users of a deployment should see what a release brings. `CHANGELOG.md` is generated by release-please from squash
commit titles; for milestone PRs those are issue and milestone names ("store, mirror and runtime robustness (M26)").
The changelog is already part of the shipped documentation site.

## Options

1. **Derive the text from `CHANGELOG.md`** at build time. Automatic, but the wording is not for users.
2. **A curated file** (`arcviz/whatsnew.json`) edited on the release PR. Good wording, one manual step per release.
3. **Curated file with fallback to the changelog.** Both costs; the fallback shows the poor wording after all.

For placement: a banner under the header, only the empty-project landing, or only a Hilfe entry.

## Decision

Option 2 with a dismissible banner (dismissal remembered per release in the browser) plus a Hilfe entry and a link to
the full changelog. The wording matters more than automation, and one short file per release is cheap. A release
without an entry shows the previous highlights instead of nothing wrong.

## Consequences

- Each release PR needs the file edited (documented in the spec; a CI check on the release PR is possible later).
- Dismissal is per browser, not per user.
