# Architecture documentation (arc42 with C4 views)

- Status: Implemented (milestone M14; runtime views as Arcviz sequence diagrams: milestone M27)
- Issue: #110, #120 (runtime views)
- ADRs: [0040 Architecture diagrams as Arcviz documents](../adr/0040-architecture-diagrams-as-arcviz-documents.md),
  [0041 arc42 as a linking layer over specs and ADRs](../adr/0041-arc42-as-a-linking-layer.md)
- Depends on: [Configurable kinds](configurable-kinds.md), [Diagram exchange](diagram-exchange.md),
  [Documentation served by the app](docs-in-app.md)

## Summary

The repository has an as-implemented specification (`docs/spec/`), design specs and ADRs, but no
document that explains the system as a whole and states how well it meets its quality goals. This change
adds that document under `docs/architecture/arc42/`:
- all twelve arc42 sections;
- C4 context, container and component views, and a deployment view;
- runtime views of the main scenarios;
- an honest assessment: quality scenarios with their status, plus risks and technical debt linked to the issues that track them.

The pages link to the existing specs and ADRs instead of repeating them.

The diagrams are drawn with Arcviz itself. They are ordinary diagram exports
(`docs/architecture/diagrams/*.arcviz.json`) that can be imported into the app and edited.
`scripts/render_architecture_diagrams.py` renders them with Arcviz's own renderer (`mermaid.render`)
into `*.mmd` files that the pages include. A test fails when a rendered file is out of date, and
another fails when the server component view no longer matches the imports in the code.

## Goals

- One entry point that explains purpose, context, structure, runtime behaviour, deployment and
  cross-cutting concepts, in the arc42 order, at the level of detail of a design review.
- An assessment that helps decide what to do next: quality goals, quality scenarios with a status
  (met, partly met, not met), and risks and debt ranked, each with its issue.
- Diagrams that dogfood Arcviz and cannot silently drift from their source or from the code.
- No duplication: details stay in `docs/spec/`, `docs/architecture/specs/` and the ADRs.

## Non-goals

- Replacing the technical specification or the module table in `docs/architecture/index.md`.
- New built-in element kinds for C4 (see ADR-0040).
- Generating diagrams from code. The diagrams are maintained by hand (in the app or as JSON), and the
  tests check them against the code.
- Sequence diagrams drawn with Arcviz before M13 (#101) is merged (see *Runtime views*).

## Design

### Pages

`docs/architecture/arc42/index.md` (overview, how to read and edit the diagrams) and one page per
section, named `NN-<slug>.md` (01–12). Each page names the specs, ADRs and spec pages it relies on.
Navigation: one group *Architecture documentation (arc42)* under *Architecture* in
`zensical.toml`, and a link from `docs/architecture/index.md`.

### Diagram documents

- `docs/architecture/diagrams/<name>.arcviz.json`: `exchange.export_document` format
  (`format: arcviz-diagram`, `schema_version: 1`). Element `properties` may carry `code` (repository path
  of the code an element stands for) and `spec` (documentation page, with an optional `#anchor`).
- `docs/architecture/diagrams/c4-kinds.json`: a kinds file (`ARCVIZ_KINDS_FILE` format) that adds the C4
  node kinds:
  - `person` (stadium);
  - `software_system`, `external_system`, `container`;
  - `container_db` (cylinder);
  - the boundaries `system_boundary`, `container_boundary` and `layer`, which are containers.

  Components use the built-in `component` kind. Relations use the built-in `connection` (runtime
  interaction) and `dependency` (code import) edge kinds. The deployment view uses only built-in kinds.
- Views: `c4-context`, `c4-containers`, `c4-components-server`, `c4-components-web-ui`, `deployment`.
- The server component view draws exactly the imports between its components, except imports of
  `model.py`, which every module but `llm/` imports. Its page says so.

### Generator (`scripts/render_architecture_diagrams.py`, `make diagrams`)

- `c4_kinds()` is a context manager that activates the C4 catalogue (`use_kinds(load_kind_catalog(...))`) and
  restores the previous one.
- `render(source)`: `exchange.parse_document` (full validation), `mermaid.render(diagram)`, and a
  `%% Generated by … from <file>. Do not edit.` comment as the second line.
- `render_all()` returns `{<name>.mmd: text}` for every Mermaid-rendered document and `{<name>.svg: text}` for
  every sequence document (the type's renderer, `render.payload`; since #120). `stale(rendered)` lists the missing or
  different files.
- Without arguments, the script writes only the stale files. `--check` writes nothing and exits 1 when anything is stale.

Pages include a diagram as:

````markdown
```mermaid
--8<-- "docs/architecture/diagrams/c4-context.mmd"
```
````

`pymdownx.snippets` resolves from the repository root, and the published site renders the fence with
Mermaid like any other. The site served by the app uses the vendored Mermaid (ADR-0043).

### Runtime views

The runtime views (section 6) are sequence diagrams. M14 wrote them as plain Mermaid `sequenceDiagram` blocks
because M13's sequence diagram type (#101) was not merged yet; M27 (#120) converted them to Arcviz sequence
documents `docs/architecture/diagrams/runtime-*.arcviz.json`, built through the sequence operations.

- The generator renders a document with its type's renderer (`render.payload`): Mermaid types into `<name>.mmd`
  (a snippet inside a `mermaid` fence), sequence documents with the own SVG renderer into `<name>.svg`, which
  starts with an XML comment naming the generator and the source. The page shows it as an image
  (`![…](../diagrams/<name>.svg)`): a standalone SVG with its own light and dark colours, no script, nothing for
  Mermaid to do; the docs build copies it like any file under `docs/`.
- Lifelines stand for building blocks of the server component view: a lifeline id is a node id of
  `c4-components-server.arcviz.json`, or `<node id>:<qualifier>` when one component has two lifelines
  (`services:diagrams`, `services:projects`). Their names are the classes and functions the scenario talks about.
- Mermaid notes and `autonumber` have no counterpart; the notes moved into the page text.
- Tests: the staleness and orphan checks cover `.svg` renders, every render is shown on an arc42 page (snippet or
  image), every runtime lifeline names a component, and the behaviour rules (#123) find no risk in a runtime view.

### Assessment content

- Section 1: the top quality goals.
- Section 10: a quality tree and scenarios, each with a status and evidence (a test, a spec or an issue).
- Section 11: risks and technical debt with severity and an issue link. It also includes the problems found while
  writing this documentation, filed as #112–#119, and a note where an open issue is already partly
  fixed in the code (#68).

## Testing

`tests/test_architecture_docs.py`:
- the five views exist;
- the rendered files are up to date, and rendering restores the kind catalogue;
- there are no orphaned `.mmd` or `.svg` files, and the generated header is present;
- every source is an importable document with the C4 kinds file;
- every view is included by an arc42 page;
- every `code`/`spec` reference exists;
- the server component view equals the imports between its components (AST of the modules, minus
  `model.py`);
- sections 01–12 exist.

`make docs` builds the pages strictly. `scripts/ci_scope.py` puts `docs/architecture/diagrams/` and
`docs/architecture/arc42/` into the `python` scope, so CI runs these tests when only the docs change.

## Migration/compatibility

The change is documentation only, plus a script and tests. To edit a diagram, start the app with
`ARCVIZ_KINDS_FILE=docs/architecture/diagrams/c4-kinds.json`, import the `.arcviz.json`, edit it,
export it over the file and run `make diagrams`.

## Open questions

None open. The choices the maintainer should review are marked *Proposed* in the ADRs.

## Decisions

- Diagrams as Arcviz documents, with C4 kinds from a kinds file shipped with the docs (not built-in kinds) and a
  generator plus staleness test:
  [ADR-0040](../adr/0040-architecture-diagrams-as-arcviz-documents.md) (Proposed).
- arc42 as a linking layer with one page per section, an explicit assessment, and temporary Mermaid runtime
  views until M13: [ADR-0041](../adr/0041-arc42-as-a-linking-layer.md) (Proposed).
